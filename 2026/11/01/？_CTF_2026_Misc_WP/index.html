其中 Hex(n) = Convert.ToHexString(RandomNumberGenerator.GetBytes(n))，每次运行都随机，所以你连”东西在哪”都要现找——这就是那句”但是不知道在哪！密钥也是！”。

① (NumberStyles)515 是什么？ 515 = 0x203 = NumberStyles.HexNumber（AllowLeadingWhite | AllowTrailingWhite | AllowHexSpecifier）。所以响应 base64 解码后的前两个字节是十六进制字符串形式的 XOR 密钥，比如 "a9" → 0xA9。我一开始按十进制理解 TryParse，看到 "a9" 还以为是协议对不上，卡了一小会儿——换成 hex 解读立刻就通了。

② 这一切防得住谁？ 防的只是”老老实实运行程序的人”：藏匿位置随机、15 秒自毁、还有断网检测。但协议本身是可逆的——XOR 密钥就写在数据开头，JSON 里的 flag 是服务器直接下发的明文，加密藏匿全部发生在本地。也就是说，根本不需要跑程序，更不需要跟它赛跑。

这正是题干”地狱一格对应主世界八格”的含义：Minecraft 里下界是主世界的八倍速捷径——别在地表跟闪电侠赛跑，直接走下界抄近道，从源头把 flag 拿走。

ezIcon

浏览器打开靶机地址不会看到网页，而是一张图片——根路径 / 直接返回了
Content-Type: image/x-icon 的文件。题目名 ezIcon、题干”小小图标”，均指向 Windows 图标文件（.ico）。

15124 字节，6 个图层的多尺寸图标。用看图软件打开是一个蓝色圆角方块 + 白色快门图案，毫无违和感。

图标类隐写的常见套路是文件结构上做手脚（附加数据、伪 chunk、目录项藏数据），先逐一排除。ICO 格式头部是 6 字节 ICONDIR，后接若干 16 字节的 ICONDIRENTRY：

解析结果：

逐项核查：

  • 目录项连续：每层 offset 紧接上一层结尾，无缝隙、无重叠，最后一张图结尾 == 文件结尾（无尾部附加数据）；

  • 每层 PNG chunk 干净：只有 IHDR / IDAT / IEND，CRC 全部校验通过，没有 tEXt / zTXt 之类的文本块；

  • 无数据藏在 IEND 后。

结构层面一无所获 → 数据只能藏在像素里。

把 6 层 PNG 全部切出来，逐层做隐写体检。先查最容易被忽视的 alpha 通道：所有图层 alpha 恒为 255，排除。再对 RGB 各通道做 LSB 位平面统计：

  • 256 主层的 LSB 几乎全为 1（图像大量纯白区域，0xff 的 LSB=1），正常；

  • 128×128 层不一样：它的 LSB 流开头 16 个字节是杂乱数据，之后才恢复全 1：

对应到画面上：该层左上角一片”纯白”里混着大量 0xfe 像素——LSB 被清零的痕迹，肉眼完全看不出。这就是payload 所在。

这题的”坏心思”就在这：多尺寸 ico 有 6 层图，zsteg 默认只扫你喂给它的那一张。
大多数人第一反应是切出最大的 256×256 主层去扫——而它恰恰是干净的。

对 128 层按逐像素 R、G、B 交错取最低位、MSB-first 拼字节重新解码

结构非常规整：3 字节 \x00\x00\x00 作 magic，第 4 字节 0x2a = 42 是 payload 长度，
紧跟着 42 字节正文——QCTF{463999a7-342b-4df6-83af-0483ab5b790e} 恰好 42 个字符，长度头自洽，确定无疑。

Good match

题目是与电脑对战，共 3 轮，盘面逐轮变大（3×4 → 4×5 → 5×6）；翻两格图案相同即配对成功并可继续翻，失配则换手；配对有连击加成，三轮累计得分高者获胜，赢了才发 flag。骰子机器对手 + 只能赢不能和的赛制，摆明了是让你写 bot —— 问题只是服务端会给 bot 下什么绊子。

结果弹窗里有个不起眼的链接”运气不好？”，指向 /docs —— 平台把完整的 API v1 文档直接挂了出来，协议、鉴权、错误码一应俱全，连示例 curl 都给了。服务端响应头为 GoodMatch/1.0 Python/3.14.7。

文档在 cells 接口下有一段加粗到发亮的说明：

该接口是只读操作：不会翻开格子，也不会改变任何游戏状态，可在任意时刻调用。返回的图案始终与该格子的真实内容一致。

这等于官方把外挂递到你手上：所谓”记忆配对”根本不用记忆——每回合把所有未配对格 GET /api/v1/game/cells/{i} 一遍，按 icon 分组，配对直接全部现形。题干第一句说的就是这件事。

顺手做了几组行为测试（第 1 轮盘面）：静置 8 秒前后两次全盘读数一致；配对成功后、故意失配后、bot 回合结束后，读数均无变化。第 1 轮是完全静态的盘面，纯背板也能过。

真让 bot 上桌，题干后半句立刻显灵。第 2 轮开始不断出现：

整局统计：17 次重排，全部发生在”翻第一格之后、翻第二格之前” —— flip1 返回的 icon 从未与读盘不符，17 次全部是在翻第二格前的单格复核中被抓到的。分布为第 1 轮 0 次、第 2 轮 3 次、第 3 轮 14 次，越打越频繁。

也就是说，服务端的反 bot 手段并不是”禁读盘”，而是在你一手进行到一半时重排剩余格子的图案：背板的玩家、缓存了扫描结果的 bot，第二格必然踩空。失配 = 换手 = bot 上桌，这正是设计者希望你体验的”格子动了，不玩了”。

但回到预言机那句描述——返回的是该格”当前承载的图案”。重排改变的只是位置映射，接口永远说真话。于是破法与重排发生在何时无关，只要求信息足够新鲜：

  1. 每手开始重读全盘：所有未配对格逐一 GET，按 icon 分组取一对；

  2. 翻第一格，用 sync=1 返回的 icon 与读盘比对 —— 不符说明翻前已重排，立即重扫定位；

  3. 翻第二格前对该格单独复核一次；图案对不上，就重扫全部剩余格，重新找出与第一格同 icon 的新位置再翻；

  4. 失配则等回合回来重来；配对成功则保持连击进入下一手。

效果：bot 的盘面信息老化窗口永远只有一个 HTTP 往返（数百毫秒），而重排恰好卡在”复核”与”翻第二格”之间的概率，被证明是零。

两处兜底：reveal 遇 409（not_your_turn / cell_already_matched）不硬刚，回快照重同步；建会话遇 503 too_many_sessions 每 5 秒重试。得分规则实测为 100 + 50×(combo−1)，combo 每轮清零——只要永不错配，回合永远在我们手里，电脑一步都摸不到。

  5. 推推论：下一步方向只能落在 {dp, dp+1}；outchar 是 (5,2)，走完 dp=d+1——每输出一个字符必然再拐 90°，21 个字符就是 21 次强制转弯。

  6. 试直觉方案，死：每字符一块 ord(ch) 格的色块去 push。因为必转弯，布局只能螺旋，而螺旋要求臂长单调收缩，112,114,105,110,116,40… 这串根本不单调，塞不进去。

  9. 推状态机（1 格色块后，问题变成”怎么直行/转弯”）：

    • pop(0,2) 在 CC=0 时 → 直行且 CC 翻成 1

    • add(1,0) 在 CC=1 时 → 直行且 CC 翻成 0

    • ⇒ pop/add 交替 = 无限直行 + CC 摆动，这是”油门”

    • inchar 要直行必须进它时 CC=1；outchar 要直行必须 CC=0

  10. 定每字符结构：奇数个填充把 CC 停在 1，然后 inchar(直行) → outchar(直行) → 用两个 gt 把方向掰回来：

21 字符 × 5 = 105 个单格色块，画布 85×22。

  1. 生成器：按解释器的状态机逐格推着放块，并加两个约束保证”画的路径 == 实际走的路径”——① 方向只从 {dp, dp+1} 里选、优先选 dp；② 新块除前驱外不与任何已有块四邻相接（否则 _try 会先摸到回头方向，程序开始倒着跑）。
